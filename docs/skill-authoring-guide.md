# 스킬 작성 가이드

llm-wiki-harness 스킬(`SKILL.md`) 작성·수정 시 단일 기준이다. 신규 스킬과 기존 스킬 수정 모두에 적용한다.

## 강제 4가지 (전 스킬)

모든 `SKILL.md`가 예외 없이 지켜야 하는 규칙이다.

1. **description** = `…할 때 사용 — <트리거·슬래시커맨드>` 형식. 트리거·증상만 담고 워크플로우 요약은 금지한다(요약은 에이전트가 절차를 건너뛰는 지름길이 된다). 한국어로 작성한다.
2. **음성/톤** = 2인칭 명령형, 짧고 단정한 문장. 위험 규칙에는 `MUST`/`NEVER` + ✅/❌ 대비를 사용한다.
3. **공통 절차 재서술 금지** — Config Gate, Content Trust Boundary, 쓰기 종료 시퀀스, QMD refresh는 스펙/AGENTS 단일 출처를 인용만 한다. 각 스킬이 다시 풀어 쓰지 않는다.
4. **링크 표기** — 본문·frontmatter 모두 `[[slug]]` 파일명만 사용한다. `index.md`는 `| [표시명](상대경로.md) | 설명 |` 마크다운 표 형식을 쓴다.

## 기본 스켈레톤 (절차형)

절차형 스킬(대다수)은 아래 헤딩 순서를 따른다. 헤딩은 한국어를 유지한다.

```
# 스킬 이름
## 개요        — 1~2줄. 무엇을 하는 스킬인가
## 언제 사용    — 트리거 + 언제 쓰지 않는가(경계)
## 워크플로우   — 번호 매긴 단계. 한 줄 압축 금지
## 품질 체크    — 종료 전 검증 항목 (쓰기 스킬만)
```

**워크플로우는 절대 한 줄로 압축하지 않는다** — 이것이 기존 스킬의 최악의 문제였다. 각 단계를 번호로 분리해 스캔 가능하게 유지한다.

## 유형별 변형 (Match the Form to the Failure)

고정 템플릿을 곧이곧대로 따르지 않는다. 스킬의 실패 유형에 형식을 맞춘다.

- **라우터형** (`using-llm-wiki`) — 스켈레톤 대신 규칙 + 라우팅 표.
- **테이블형** (`wiki-lint`) — 체크 표 중심으로 구성.
- **read-only형** (`wiki-query`·`wiki-status`) — "쓰지 않는다" 경계를 강조하고, 품질 체크 대신 검색 사다리(search ladder)를 둔다.
- **위험 지점** — 위험이 있는 지점에만 전용 장치를 투입한다: 금지 박스, 명시 게이트, 강조 규칙, 불변성 규칙 등. 위험이 없는 곳에 장치를 남발하지 않는다.

## 장치 사용 규칙

- **mermaid 흐름도** — 비자명한 분기가 있을 때만 사용한다. 선형 절차는 번호 목록으로 충분하며 흐름도를 쓰지 않는다.
- **Red Flags / 합리화(Excuse\|Reality) 표** — 규율 위반이 실제로 우려되는 지점에만 배치한다. 남용하면 신호 대 잡음비가 떨어진다.
